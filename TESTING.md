## Media storage backend (Supabase Storage or Cloudflare R2)

Media is stored in Supabase Storage (`social-media` bucket) unless every R2 variable below is set **and** `MEDIA_BACKEND=r2`. Set them as function secrets (`supabase secrets set NAME=value --project-ref <ref>`; locally in the git-ignored `supabase/functions/.env`), then redeploy `social`, `group-photos` and `refresh-campus` so new isolates pick them up. Never commit or print the values.

| Variable | Purpose | When absent |
|---|---|---|
| `MEDIA_BACKEND` | `r2` sends new attachment uploads to R2. Any other value, or unset, keeps Supabase Storage. | Supabase Storage (previous behaviour, byte for byte) |
| `R2_ACCOUNT_ID` | Cloudflare account id; the S3 endpoint is `https://<id>.r2.cloudflarestorage.com` | backend stays `supabase`; existing `r2/` objects cannot be read or deleted |
| `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` | R2 API token (Object Read & Write, scoped to the bucket) | as above |
| `R2_BUCKET` | bucket for post media (`public/` keys); the only bucket a custom domain may ever be attached to | as above |
| `R2_PRIVATE_BUCKET` (optional) | a second bucket for room/DM media (`private/` keys), presigned reads only; **never attach a custom domain to it**. Must differ from `R2_BUCKET`. Keep it set once used, or existing `r2/private/` objects cannot be read or deleted | room/DM media stays on Supabase Storage (authenticated reads) |
| `R2_PUBLIC_BASE_URL` (optional) | custom-domain CDN base such as `https://media.example.edu`; used only for post media (`public/` keys), and only together with the two purge variables below | every R2 read is a 24 h presigned S3 GET |
| `R2_CDN_ZONE_ID`, `R2_CDN_PURGE_TOKEN` (optional) | the Cloudflare zone of that domain and an API token with only the Zone → Cache Purge permission; deleting an `r2/public/` object purges its CDN URL | CDN URLs are not issued (a cold-start warning `media_cdn_disabled` is logged if `R2_PUBLIC_BASE_URL` is set) |
| `R2_ENDPOINT_OVERRIDE` | local tests only (MinIO or a stub); never set in production | the account's S3 host |

- **Flip to R2:** apply migration `20261005190000_r2_media_revocation` first (it queues the R2 objects of deleted/moderated posts and deleted attachment rows; check with `tools/test-r2-media-revocation.sql`). Then set the four `R2_*` credentials and `R2_PRIVATE_BUCKET`, then `MEDIA_BACKEND=r2`, and redeploy. The cold-start log line `{"event":"media_backend","backend":"r2","r2_reachable":true,"private_bucket":true,"cdn":false}` confirms it. Objects already in Supabase keep their bare paths and are still served from Supabase; new ones get `r2/public/…` (post media) or `r2/private/…` (rooms/DMs, only with `R2_PRIVATE_BUCKET`) paths. Memes, group photos and activity posters stay on Supabase until a migration relaxes their path checks.
- **Turn on the CDN (later, optional):** only after the migration above is applied. Attach the custom domain to `R2_BUCKET` only, set `R2_CDN_ZONE_ID` and `R2_CDN_PURGE_TOKEN`, then `R2_PUBLIC_BASE_URL`, and redeploy (`"cdn":true` in the log line). Before relying on it, prove room media is unreachable there: `curl -sI https://<cdn-host>/private/<any-key>` must not return 200 (the private bucket has no domain, so it is a 404). A deleted post's media stops being served once the hourly worker deletes the object and purges its URL.
- **Flip back:** unset `MEDIA_BACKEND` (or set it to anything but `r2`) and redeploy. Keep the R2 credentials so existing `r2/` objects stay readable and deletable.
- **Cloudflare dashboard (no code):** create both buckets; for the CDN attach a custom domain to the post-media bucket only (never the private one), optionally a WAF custom rule on that hostname blocking any path not starting with `/public/` as defence in depth, a Cache Rule "Eligible for cache" that respects origin headers, and Smart Tiered Cache. Create the purge token scoped to that zone with only Cache Purge. Post objects carry `Cache-Control: public, max-age=31536000, immutable`, room/DM objects `private, max-age=86400`; keys are random UUIDs and never reused.
- **Tests without keys:** `deno test --allow-read --allow-net=127.0.0.1 supabase/functions/_shared/` covers signing, the private bucket, CDN gating and purging, and dispatch with fixed fake credentials; `python3 tools/test-media-store.py` checks the deployed default (inline `media_data`, revocation on post deletion); `tools/test-r2-media-revocation.sql` (psql as the database owner, rollback) checks the revocation triggers once the migration is applied.
