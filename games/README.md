# Maroon games

Native navigation hosts an offline, bundled Three.js table in WKWebView. Pool uses Matter.js for rigid-body collision resolution. Cup pong uses cannon-es for the ball, gravity, table, cup walls, and rims. The same pure simulation module runs in the Supabase Edge Function; clients submit shot inputs rather than scores or ball positions. Online chess uses chess.js legal moves and game termination. The existing native SceneKit chess practice board and Swift rules remain available offline.

## Build and verification

From the repository root:

```sh
npm ci --prefix games --ignore-scripts
npm run build --prefix games
npm test --prefix games
python3 tools/test-games.py
python3 tools/test-games-anonymous.py
```

The build produces `MaroonSocial/Resources/game-runtime.js`, `game-table.html`, runtime licenses, and `supabase/functions/games/engine.js`. Commit generated bundles so the iOS build needs neither Node nor internet access. Rebuild both bundles whenever changing `src/engine.js`; a rules change also requires a new `RULES_VERSION` and migration plan for existing matches. Regenerate the Xcode project using the repository’s normal XcodeGen workflow after adding files.

The Node tests compare source and deployed-bundle simulation results exactly. They cover repeatable multi-ball breaks, collision events, foul/ball-in-hand rules, finite trajectories, every cup being physically reachable, a final-cup win with other cups removed, hostile/out-of-range input, and legal chess/checkmate. Tests intentionally use real libraries, not physics mocks.

`tools/test-games.py` creates three synthetic accounts against the configured project and deletes those accounts in `finally`. It verifies accepted-DM invitation gates, durable invitation cards, acceptance/decline, unrelated-user denial, wrong-turn rejection, illegal input, two concurrent turns (one successful CAS), identical peer state/replay, nonce retries, persistent match listing, resignation, and block revocation. It uses only public API configuration and private synthetic device tokens; it never logs bearer tokens. Do not run this script against an unrelated project. A hash-only fixture receipt is saved under `/tmp` for audit.

## Physics 2.1 and source review

New matches use `maroon-games-2.1.0`. Existing `maroon-games-2.0.0` sessions route through the frozen `legacy-engine-v2.js`, preserving their outcomes and stored replays. The native bundle and Edge bundle include both versions; the server decides from canonical state, never a client-supplied version. New invitations require the database version allowlist migration before deploying the updated Edge Function.

Pool uses fixed 240 Hz stepping, a nonlinear stroke curve from gentle rolls to a 5 m/s full break, constant 0.22 m/s² rolling deceleration, 0.96 ball restitution, and a distinct 0.82 cushion impact restitution. Matter normally combines restitution using the maximum, so the contact pair must explicitly use the cushion value. The renderer still interpolates canonical frames; the felt, wood, lighting, balls, and overhead aiming appearance remain the same.

`pong-cups.js` adapts the wall/bottom separation and bottom-contact scoring from [JBallin’s Swift `ARViewController.swift`](https://github.com/JBallin/beer-pong/blob/8f1e420ffce5bc396105e49450651e306d4089b9/beer-pong/ARViewController.swift). The original assigns separate static concave physics to cup sides and bottom, lowers their restitution, and sinks the cup when a ball contacts the bottom. Our adaptation uses deterministic Cannon bodies, tapered overlapping slats matching the visible cup, a real absorbing floor, and explicit bottom-body identity. It does not rely on contact node ordering. The original AR tap control, assets, and above-one table/floor restitution are not used. This is adapted Swift game physics design; the shipped simulation remains shared JavaScript, not a native SceneKit replacement. The complete MIT notice is included in `licenses/JBallin-beer-pong.txt` and the app’s bundled licenses.

Other reviewed native sources: [jdstruck/Pool-ios](https://github.com/jdstruck/Pool-ios/tree/bbafae5d4acedaa5ccd8157a1fa826ea52c00d41) has no license and was not copied; [nullLuli/Billiards](https://github.com/nullLuli/Billiards/tree/8db39ef9c99be9af7013b0c2590dbe5dc6c03f58) is MIT but models a single animated ball reflecting off rectangular boundaries, without ball-ball or pocket rules; [SpriteKit-Box2D](https://github.com/AchrafKassioui/SpriteKit-Box2D/tree/f8b758b73cd88ac486634a7f687f1e4ebf17acac) is an Apache-2.0 Swift integration for the MIT Box2D C engine, a credible future native backend but not a pool game. A native-only replacement would differ from the authoritative Edge simulation; any future migration must deploy the same pinned engine to native and server and prove trajectory parity first.

`physics-quality.test.mjs` checks measured roll deceleration and stopping, cushion reflection/energy loss, break speed, head-on momentum transfer without energy creation, a real sphere falling through an open cup mouth and resting on its bottom, and exact old/new server parity. These regressions catch physical defects; they do not establish that touch feel is enjoyable. Native gesture tests and manual play are still required after tuning.

## Interaction and rules

Pool: touch the felt to aim, or pull backwards and release to set direction and power. The cue, dashed contact guide, and ghost ball show the next contact. Fine aim and power controls are available without precise gestures. A foul enables **Place cue**; only an empty legal spot is accepted. Sound is off by default and optional; physical impacts/pockets also produce native haptics. Pool aiming is always flat overhead. Perspective is available during replays, and the table returns flat before the next turn. **Rules** explains the exact variant.

Pool uses casual eight-ball: first legal pocket assigns groups, own pockets retain the turn, and scratch/no contact/wrong first contact/no subsequent cushion or pocket gives ball in hand. Clear your group before the eight. An early or fouled eight loses; an eight on the break is respotted. Called pockets, professional break-point rules, jump shots, masse and cue elevation are not implemented. Spin is bounded in the protocol and changes angular velocity in the planar engine; the current UI sends zero rather than promising realistic English.

Cup pong: alternate throws at your own six-cup rack. Pull down to add power; lateral pull adjusts direction independently, so a longer pull does not swing the aim. The screen-space control remains consistent in either camera view. A short tap aims without throwing; cancelled touches never throw. Final release coordinates are used even when WebKit coalesces pointer moves. The arc and contact ring use the actual Cannon solver without consuming a turn, throttled to at most one update per 80 ms with identical-input caching. Fine aim/power controls remain available. Choose **Arc throw** or **Bounce throw**; the solver handles table bounce, rim rejection, cup-wall deflection and sinking. Six cups wins. No redemption round or same-cup bonus. There are no random hit probabilities or target buttons that automatically award points.

Online chess supports castling, en passant, promotions, checkmate, stalemate, repetition, fifty-move and insufficient-material draws through chess.js. Tap a 3D piece and destination, or choose an accessible algebraic move button. White is the inviting player.

## Online protocol and privacy

`POST /functions/v1/games` authenticates `X-Social-Token` through the shared device-member account. The public API key is not a user identity. JWT verification is disabled only because this endpoint performs its own device-token authentication. Tokens are hashed before RPC calls. `games_private` tables are private, RLS enabled, and service-role only. RPC execution is revoked from public/anon/authenticated.

- `invite {room,kind,nonce}`: accepted direct conversation only; server constructs initial state. Invitation appears as a chat card. Maximum five pending invitations and thirty/day. Invitations expire after seven days.
- `accept|decline|cancel {id}`: only the correct participant may respond. Acceptance locks the two seats and activates the persisted game.
- `list`, `get {id}`: participant-only snapshots include names and seat, never private member IDs or credentials. Anonymous post-origin conversations expose only `Player 1`/`Player 2` aliases in every response, including invites, reads, lists and turns.
- `turn {id,version,nonce,input}`: authenticate and read the current canonical state; simulate outside the transaction; commit under a session row lock only if version, participant, turn and active status still match. Client-supplied state, winner, or replay is ignored. Nonce retries are idempotent and changed input under an existing nonce is rejected.
- `forfeit {id}`: ends an active match with the other seat as winner.
- Rematch creates another invitation requiring acceptance. Leaving a screen never resigns.

Banned or blocked participants cannot access or mutate a match. Physics is computed once on the server; both clients interpolate the same bounded replay frames. Native polling resumes on foreground and ignores older-version responses. A network error restores the controls and keeps the nonce for a retry of the same input. No optimistic win/score is persisted.

## Limits

This is casual turn-based play, not a certified billiards simulator or a real-time tournament service. Physics is deterministic within the pinned engine/version and fixed-step settings; server replay remains authoritative even on platforms with numerical differences. Persistent online accounts are device credentials; university SSO and cross-device credential recovery are separate product work. Native simulator screenshots and touch QA are required in addition to these protocol tests before a release.

Native integration tests live in `MaroonSocialTests/GameWebViewTests.swift`. Run the iOS test scheme (or select that class) on a simulator. They load the offline bundled HTML in actual WKWebViews, wait for real WebGL initialization, execute a full pool break and cup throw, verify score/turn updates and non-scoring manual replay, and exercise online pool/pong/chess input messages followed by canonical state and replay. The tests include phone-size viewport checks and attach screenshots. `Fixtures/game-states.json` contains synthetic initial states and canonical replay from this pinned engine, with no account or backend data.

Gesture regressions: `controls.test.mjs` checks screen-space stability, scale invariance, bounds, cancellation intent, and physical reachability of all six cups. Native `GameWebViewTests` compares missing/stale/complete pointer-move streams, flat pool aiming, and stable pong direction. `GameGestureUITests` exercises UIKit-delivered press/drag input in the bundled WebView; only a passed simulator run verifies that native gesture path.

## Campus matchmaking

Explore game cards open an online lobby. **Find a player** joins the selected game's campus queue; local two-seat controls are available only through the explicitly labeled **Practice on this phone** link. A search has one device-member identity, a unique nonce, and a 45-second heartbeat expiry. The app polls every two seconds only while that lobby is visible and active, and cancels on leaving/backgrounding. Cancel receipts also reject out-of-order HTTP joins. A match made concurrently with cancellation remains in My matches.

The server pairs eligible unblocked members atomically under a short queue lock, creates an anonymous accepted match conversation, assigns distinct seats, and initializes canonical state itself. The same existing turn gateway checks the actor's seat, current turn, version, and input nonce. Search retries return the same match; starting another search resumes an existing active match of that kind. New matches are capped at 30/member/day. Queue and cancellation tables are private, RLS-enabled, and service-role-only; no client reads the queue or chooses its opponent's identity.

Validation: `tools/test-game-matchmaking.py` exercises all three games using disposable synthetic accounts, seat ownership, shared replay, resumes, cancellation races, four concurrent searches, blocked-player exclusion, and cleanup. `tools/test-game-matchmaking-security.sql` runs entirely in a rolled-back transaction and checks ACLs, expiry, late joins, banned players, anonymous projections and account-delete cascades. Native `GameMatchmakingTests` checks cancellation and polling lifecycle.

### Additional source review requested October 3

- [piqnt/polymatic-example-eight-ball](https://github.com/piqnt/polymatic-example-eight-ball) is an MIT TypeScript pool example using Planck/Box2D, with server-owned turns and pointer-to-cue input. Its rules randomly assign groups and use a simplified scratch reset. It is a useful protocol/control reference; replacing the current pinned engine would require a new version and cross-runtime trajectory tests to preserve existing matches. No code from it has been copied.
- [OpenBubbles/OpenPigeon](https://github.com/OpenBubbles/OpenPigeon) currently targets Android/OpenBubbles and uses PolyForm Shield for current code, with separately restricted assets. It is not a native Swift package; neither its code nor assets are bundled here.
- [trace-swift-ui/swiftui-pong-game](https://github.com/trace-swift-ui/swiftui-pong-game) implements two-paddle Pong in SwiftUI/Combine, rather than a thrown ball/cup simulation, and the checked-out repository supplies no license. Its code is not copied into cup pong.

## Browser pool evaluation (2026-10-04)

The separate [`web-pool-prototype`](web-pool-prototype/README.md) is a runnable, branded GPL-3.0 preview of [tailuge/billiards](https://github.com/tailuge/billiards/tree/9cd48c5cc0986f86e5514d21f7668aa408d538ea), including its unmodified spin/sliding/rolling/cushion physics and 61 passing physics regressions. It is packaged for static Vercel hosting with matching source download and license notices. It supports public local practice and a separate authoritative 3.0 opponent queue through short-lived pool-only sessions from the native app. The new Edge solver runs the same pinned physics and returns canonical frames; a live three-client regression matched server and local state/replay exactly. Existing 2.x games/invitations remain unchanged. New chat Pool invitations and explicit same-opponent rematches use 3.0, preserving anonymous/discovery/group aliases and recipient acceptance. Practice is published at https://maroon-social-games.vercel.app; hosted two-device interaction remains a separate validation step from the API proof. Its README documents the interface and remaining licensing/distribution considerations.

Other web candidates inspected: [Polymatic eight-ball](https://github.com/piqnt/polymatic-example-eight-ball) is permissively licensed but has simpler game rules and planar physics; [elijah-atkins/Billiards](https://github.com/elijah-atkins/Billiards) and [jaks6/WebGL-Billiards](https://github.com/jaks6/WebGL-Billiards) did not expose a reusable license in the inspected repository and were not copied. For cup pong, the high-ranked JS repositories reviewed were mostly unlicensed demos or tournament scorekeepers, not a mature replacement with server rules; no better licensed 3D cup-pong engine was established. The current pinned MIT cannon-es solver and MIT Swift cup-contact adaptation remain the working authoritative path. Table-tennis/paddle Pong projects are a different game and were not substituted for cup pong.

## Cup Pong 2.2 (2026-10-04)

The ball formerly retained almost all horizontal speed because it used only 0.012 linear damping. New 2.2 uses force opposite velocity with the [NASA drag equation](https://www1.grc.nasa.gov/beginners-guide-to-aeronautics/drag-equation/), a 40 mm / 2.7 g ball, density 1.225 kg/m³ and explicit smooth-sphere approximation Cd 0.47. This is a bounded physical model, not wind-tunnel calibration for a specific ball. Arc and bounce launch ranges are retuned; all 6 cups are reachable through both modes. Rendered cups/table remain unchanged. Cup wall and absorbing bottom contact still use the licensed Swift-project adaptation.

The guide now stops the exact solver at its first relevant contact instead of completing an entire miss. Desktop sample measured ~1.1 ms median / 3.1 ms p95 versus ~4.1 / 6.3 ms for full replay; these are observations, not a mobile performance guarantee. Frozen `legacy-engine-v21.js` and 2.0 resolver retain prior trajectories. Source/server bundles and synthetic native fixtures were rebuilt together; the scoring fixture now uses a real 30% arc. 19 Node regressions, rollback matchmaking security, and live DM pool/pong/chess authorization/CAS/replay tests passed after deployment. No new native gesture or player-feel result is claimed here.
